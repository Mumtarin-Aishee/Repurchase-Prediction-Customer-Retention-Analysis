# Data Dictionary — Order Report Export

Documentation for the raw order-level export used as the input to the [repurchase-interval analysis](./README.md) (Phase 1: Power BI/DAX model) and the AI-driven analysis (Phase 2: Claude + weekly automation).

> **Privacy note:** this file documents *structure and data-quality characteristics only*. No customer names, order numbers, invoice numbers, or exact revenue figures from the real export appear below — every example row is fabricated to illustrate the format, and every statistic is either a structural count (row/column counts, null rates, cardinality) or deliberately generalized where it could reveal real business figures.

## Overview

| | |
|---|---|
| **Source** | Order export from the client's e-commerce store (WooCommerce-style order/invoice report) |
| **Granularity** | One row per completed order |
| **Time coverage** | ~20 months, January 2025 through August 2026 |
| **Format** | CSV, UTF-8, comma-delimited with quoted fields |
| **Columns** | 12 |
| **Rows** | 5578 |

## Column reference

| Column | Type | Description | Format notes |
|---|---|---|---|
| `Date` | datetime (text) | Order timestamp | `M/D/YYYY H:MM` (24-hour), e.g. `8/31/2025 23:19`. Parses cleanly — no malformed dates found in the export. |
| `Order #` | integer | Store's internal order ID | Unique per row; one-to-one with rows in this export. |
| `N. Revenue (formatted)` | currency (text) | Order revenue, pre-formatted for display | Stored as **text**, not a number — prefixed with a currency symbol (৳) and comma thousands separators (e.g. `৳2,999`). Must be stripped and parsed before any aggregation. |
| `Status` | categorical | Order status | Every row in this export is `completed`. (The production pipeline also accepts `processing` per its own logic, but this particular export appears pre-filtered to completed orders only — worth confirming against the source system rather than assuming other statuses are simply absent from the store.) |
| `Customer` | text | Customer display name as entered at checkout | Free text, not a stable ID — see [`data-quality-issues.md`](./data-quality-issues.md) for the ways this breaks in practice. |
| `Customer type` | categorical | `new` or `returning`, as tagged by the store at the time of the order | Two-value field, no missing values. |
| `Product(s)` | delimited text | Line items in the order | Format: `{qty}× {full product name}`, multiple items comma-separated, e.g. `2× Product A, 1× Product B`. **~11% of rows have this field blank** even though the order has one or more items sold — see [`data-quality-issues.md`](./data-quality-issues.md). Orders range from 1 to over 20 distinct product lines. |
| `Items sold` | integer | Total unit count across all line items in the order | Typically single digits; a small number of bulk/wholesale-style orders run much higher. |
| `Coupon(s)` | text | Coupon code(s) applied, if any | **Present in under 2% of rows** — the large majority of orders have no coupon. |
| `Net Sales` | integer | Order value net of one specific adjustment | This is *not* simply "revenue minus tax" — see [`data-quality-issues.md`](./data-quality-issues.md) for what it actually isolates. |
| `Attribution` | categorical (semi-free text) | Marketing source/channel for the order | Values follow a loose `Source: X` / `Referral: X` / `Direct` / `Organic: X` pattern. ~20+ distinct values observed; see [`data-quality-issues.md`](./data-quality-issues.md) for formatting inconsistencies. |
| `Invoice Number` | integer | A separate sequential invoice ID, distinct from `Order #` | Appears to be generated by a different counter than the order ID (likely a separate invoicing system/plugin) — the two should not be treated as interchangeable keys. |

## Data quality

This export has several quirks worth knowing before you build anything on top of it — currency-as-text formatting, a revenue field that disagrees with itself, internal accounts mixed into the customer list, and more. See **[`data-quality-issues.md`](./data-quality-issues.md)** for the full write-up, plus the preprocessing steps used to handle each one.
